# Glossary - Forge Engineering Lifecycle Framework

## A

### ADR (Architecture Decision Record)
A document that captures an important architectural decision made along with its context and consequences. ADRs are immutable once accepted; new decisions create new ADRs.

### Acceptance Criteria
Specific conditions that must be met for a requirement to be considered complete and satisfactory.

### Analysis
The phase of evaluating requirements, assessing feasibility, identifying risks, and performing trade-off analysis.

### Artifact
Any documented output produced during the SDLC, including reports, plans, specifications, and designs.

## B

### Best Practice
A technique or methodology that has been generally accepted as superior to alternatives based on proven results.

### Blue-Green Deployment
A deployment strategy that uses two identical production environments (blue and green) where traffic is switched between them for zero-downtime deployments.

### Branching Strategy
A convention for how code branches are created, merged, and managed in version control (e.g., GitFlow, trunk-based).

## C

### Canary Deployment
A deployment strategy that gradually rolls out changes to a small subset of users before full deployment.

### CI/CD (Continuous Integration/Continuous Deployment)
A practice of automating the building, testing, and deployment of code changes.

### Code Coverage
A measure of what proportion of source code is executed during testing (line coverage, branch coverage, path coverage).

### Code Review
A systematic examination of source code by peers to identify issues, improve quality, and share knowledge.

### Competitive Analysis
Evaluation of competing solutions or products to understand their strengths, weaknesses, and differentiation.

### Constraint
A limitation or restriction that affects the solution space (technical, business, regulatory, organizational).

### Context Preservation
The practice of maintaining and transferring relevant information across workflow phases and interactions.

## D

### Debug
The process of identifying, isolating, and resolving defects in software.

### Decision Matrix
A quantitative technique for evaluating options against multiple weighted criteria.

### Defect
A flaw in software that causes it to behave unexpectedly or produce incorrect results.

### Design
The phase of creating system architecture, component designs, data models, and API specifications.

### Design Pattern
A reusable solution template for commonly occurring problems in software design.

### DRY (Don't Repeat Yourself)
A principle aimed at reducing repetition by abstracting common functionality.

## E

### Edge Case
An unusual or extreme condition that lies outside the normal operating parameters of a system.

### End-to-End Test (E2E)
A test that verifies a complete user workflow from start to finish, including all integrated components.

### Entry Criteria
Conditions that must be met before a phase or activity can begin.

### Exit Criteria
Conditions that must be met before a phase or activity can be considered complete.

## F

### Feasibility Study
An assessment of the practicality of a proposed project, considering technical, economic, and operational dimensions.

### Functional Requirement
A specification of what a system should do (behaviors, features, functions).

## G

### Greenfield Project
A new project developed from scratch without constraints from existing systems.

### gRPC
A high-performance remote procedure call framework using Protocol Buffers.

## H

### Health Check
An automated test that verifies a system or component is functioning correctly, typically exposed via an endpoint.

## I

### Integration Testing
Testing that verifies the interaction between components or systems.

### Issue
A tracked item representing a bug, task, or feature request.

## K

### KISS (Keep It Simple, Stupid)
A principle advocating for simplicity in design and implementation.

### KPI (Key Performance Indicator)
A measurable value that demonstrates how effectively a project or organization is achieving objectives.

## L

### Legacy System
An older system that is still in use, often based on outdated technology.

### Load Balancer
A device or service that distributes incoming network traffic across multiple servers.

## M

### Microservices
An architectural style where an application is composed of small, independent services communicating over APIs.

### Migration
The process of moving from one technology, platform, or architecture to another.

### Modernization
The process of upgrading, migrating, or refactoring existing systems to improve quality attributes.

### MoSCoW
A prioritization technique: Must have, Should have, Could have, Won't have.

## N

### Non-Functional Requirement
A specification of how a system should behave (performance, security, reliability, usability).

## O

### OpenAPI
A specification for describing, producing, consuming, and visualizing RESTful web services (formerly Swagger).

## P

### Phase
A distinct stage in the SDLC with specific objectives, steps, and outputs.

### PoC (Proof of Concept)
A small implementation to demonstrate the feasibility of an approach or technology.

### Pull Request (PR)
A mechanism for proposing code changes and requesting review before merging.

## Q

### Quality Gate
A checkpoint that must be passed before proceeding to the next phase, defined by specific criteria.

### Quality Metric
A quantitative measure of some aspect of software quality.

## R

### Refactoring
The process of restructuring existing code without changing its external behavior.

### Regression Testing
Testing that verifies existing functionality still works after changes.

### Requirement
A condition or capability that must be met by a system.

### Research
The phase of gathering, evaluating, and synthesizing information to inform decisions.

### REST (Representational State Transfer)
An architectural style for designing networked applications using HTTP methods.

### Risk
An uncertain event that could have a positive or negative effect on project objectives.

### Rollback
The process of reverting a system to a previous state, typically after a failed deployment.

### Rolling Deployment
A deployment strategy that incrementally updates instances one at a time.

## S

### SDLC (Software Development Lifecycle)
The process of planning, creating, testing, and deploying software.

### Smoke Test
A basic test that verifies the most critical functionality of a system is working.

### SOLID
Five design principles: Single responsibility, Open-closed, Liskov substitution, Interface segregation, Dependency inversion.

### Stakeholder
Any person or group with an interest in or affected by the project.

### SWOT Analysis
A framework evaluating Strengths, Weaknesses, Opportunities, and Threats.

## T

### Technical Debt
The implied cost of additional rework caused by choosing an easy solution now instead of a better approach.

### Trade-off
A compromise where one thing is given up in exchange for another.

### TRL (Technology Readiness Level)
A measure of technology maturity from 1 (basic principles observed) to 9 (proven in operation).

## U

### Unit Test
A test that verifies the correctness of an individual function or method.

### User Story
A description of a feature from the perspective of the end user.

## V

### Verbosity
The level of detail included in output (minimal, standard, detailed).

## W

### Work Breakdown Structure (WBS)
A hierarchical decomposition of the total scope of work into manageable tasks.

## Y

### YAGNI (You Aren't Gonna Need It)
A principle stating that functionality should not be added until it is necessary.
